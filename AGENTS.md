# Инструкции для агентов

## Текущая стадия

Продуктовый, архитектурный и технический дизайн утверждён. Кодовая база приложения, её CI и канонические implementation-команды ещё не созданы. Не объявляй документ доказательством реализации и не выдумывай команды, структуру пакетов или test targets.

## Перед началом задачи

Перед планированием или изменением прочитай `doc/README.md` и выбери минимальный маршрут по типу задачи:

- `doc/product/` определяет пользовательское поведение, продуктовые границы и приёмку;
- `doc/architecture/` определяет модули, зависимости, долговечные факты и восстановление;
- `doc/technical/` определяет платформенные протоколы, форматы, безопасность и эксплуатацию.

До изменения:

1. назови ограниченный scope;
2. определи нормативных владельцев;
3. для кода зафиксируй контракт вертикального среза из `doc/engineering/development-workflow.md`;
4. отдели действующее требование от истории обсуждений, планов и текущей реализации.

При противоречии комментария нормативному документу нормативный документ имеет приоритет.

## Oracle-first разработка

- Ожидаемое поведение protected acceptance и contract tests выводится из нормативного владельца, а не из production-кода.
- Не ослабляй protected oracle ради зелёного результата. Его изменение означает изменение требования либо доказанную ошибку oracle и требует отдельного обоснования.
- Для bug fix докажи `FAIL` на исходной реализации и `PASS` после исправления с тем же oracle.
- Для нового поведения сначала зафиксируй наблюдаемый и запрещённый результаты, затем реализуй минимальный путь к результату PR-среза.
- Fake не является эталоном. Один contract suite проверяет одинаковую семантику fake и реального adapter.
- Зелёные тесты без прослеживаемого oracle не доказывают корректность.
- После implement-фазы выполни обязательный независимый verify-gate по `doc/engineering/development-workflow.md`. Срез не завершён без clean-context verdict `PASS`.

Восемь пунктов продуктовой приёмки являются волнами реализации, а не единицами pull request. Активный план декомпозирует волну на milestones, а milestone — на вертикальные PR-срезы. Один PR-срез даёт один независимо проверяемый пользовательский, эксплуатационный или публичный контрактный результат.

Устойчивые ID обязательных сквозных сценариев находятся в `doc/architecture/recovery.md`. Один сценарий может охватывать несколько PR-срезов и требовать нескольких примеров, property tests и fault-injection точек. Milestone не завершён без отдельного сквозного clean-context verdict `PASS` на интегрированном состоянии.

## Git-интеграция

- Каждый вертикальный PR-срез выполняется в отдельной ветке и попадает в `main` только через pull request.
- Merge разрешён только после обязательных проверок и clean-context verdict `PASS` для текущей версии pull request; новый commit отменяет прежний verdict.
- Используй squash merge. Прямой push в `main` запрещён.

## Why-комментарии

При создании, изменении, рефакторинге или ревью кода используй Agent Skill `maintain-why-comments`, если он доступен. Если клиент не поддерживает skill, следуй `doc/engineering/why-comments.md`.

Фундаментальные документы владеют стратегией и системными инвариантами. Комментарии в коде объясняют только локальную тактику: почему конкретная реализация обязана выглядеть именно так и что нарушит очевидная альтернатива.

Не копируй фундаментальные правила в код. Ссылайся на устойчивый документ или раздел и обновляй либо удаляй комментарий вместе с изменившейся причиной.

## Архитектурные границы

- Модулей ровно четыре: `monitoring`, `synthesis`, `delivery`, `operations`.
- Полным запуском владеет только `operations`.
- Предметные модули не вызывают друг друга и не импортируют внутренние реализации соседей.
- Telegram-типы не проникают в контракт `synthesis`.
- Реализации внешних портов явно связываются в composition root; runtime discovery и plugin registry запрещены.
- Секреты существуют только через `SecretStore` и не попадают в код, конфигурацию, логи или диагностические артефакты.

## Безопасность изменений

- Не передавай секреты через чат, URL, stdout, JSON, логи или агент-доступный терминальный ввод.
- Не заменяй `SecretStore` конфигурационным значением, переменной в коде или тестовой fixture, способной попасть в артефакты.
- Не выполняй внешнее действие, миграцию или изменение системного расписания, если задача ограничена анализом либо документацией.
- Не изменяй нормативное поведение попутно с реализацией. Сначала выдели отдельное изменение владельца.

## Завершение и доказательства

Перед завершением изменения:

1. выполни применимые проверки среза и полный доступный verify-профиль;
2. проверь архитектурные границы и соседние Why-комментарии;
3. определи затронутых владельцев документации;
4. обнови их либо явно зафиксируй `documentation impact: none`;
5. выполни `python tools/check_docs.py`;
6. сообщи точные команды и результаты, не подменяя отсутствие проверки планом или ожидаемым результатом;
7. не объявляй завершение при несинхронизированной документации или непроверенном protected oracle.

Пока приложения нет, каноническими исполнимыми командами являются только документированные проверки документации:

```console
python tools/check_docs.py
python tools/test_check_docs.py
```
