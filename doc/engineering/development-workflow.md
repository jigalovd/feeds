# Разработка проверяемыми вертикальными срезами

**Назначение:** исполнимый workflow реализации и исправления поведения для разработчиков и ИИ-агентов  
**Не является:** источником продуктовых, архитектурных или технических правил  
**Связанные документы:** [карта документации](../README.md), [приёмка](../product/acceptance.md), [восстановление](../architecture/recovery.md), [тестирование](../technical/testing-observability.md)

После чтения этого руководства исполнитель должен уметь провести один ограниченный срез от нормативного требования до независимо проверенного результата, не выводя ожидаемое поведение из собственной реализации.

## Основной принцип

Код и тесты являются двумя реализациями одного требования. Зелёный тест доказывает корректность только тогда, когда его oracle — ожидаемое наблюдаемое поведение — прослеживается до нормативного владельца и не был подобран по результату проверяемого кода.

Рабочий цикл:

```text
нормативное требование
→ фиксация oracle
→ protected acceptance или contract test
→ реализация и developer tests
→ независимая атакующая проверка
→ полный verify
```

Тесты не становятся источником истины. При расхождении теста с нормативным документом сначала определяется ошибочный артефакт; тест не исправляется автоматически под текущее поведение.

## Контракт среза

До изменения приложения исполнитель фиксирует:

```text
Slice:
Нормативный владелец:
Требование:
Наблюдаемый результат:
Запрещённый результат:
Источник oracle:
Protected tests:
Дополнительные проверки:
Documentation impact:
```

Контракт ограничивает работу одним пользовательским или эксплуатационным результатом. В него не включаются соседние улучшения, которые не нужны для прохождения выбранного сценария.

Если требование неоднозначно, реализация не начинается: сначала обновляется нормативный владелец. Если требование уже утверждено и однозначно, отдельное согласование технических деталей не требуется.

## Роли тестов

| Роль | Источник ожидаемого поведения | Полномочия implementer |
|---|---|---|
| Protected acceptance | Продуктовая приёмка и архитектурные сценарии | Запускать и дополнять входы; не менять семантику oracle без изменения требования |
| Port contract | Публичный контракт порта и платформенный протокол | Реализовывать fake и adapter; не задавать им разные правила |
| Developer tests | Локальный дизайн среза | Создавать и изменять в пределах нормативного поведения |
| Adversarial verification | Инварианты, мутации и контрпримеры | Получать результаты после implement-фазы; не ослаблять проверку ради текущего кода |

Protected означает защищённость ожидаемого поведения, а не неизменяемость файла. Переименование, устранение дублирования, замена fixture или техническая адаптация допустимы, если oracle не изменился.

## Порядок работы

### 1. Получить минимальный контекст

Исполнитель начинает с [карты документации](../README.md), выбирает маршрут задачи и читает только нормативных владельцев среза. История обсуждений, старые планы и текущая реализация не заменяют действующие документы.

### 2. Зафиксировать oracle

До подробного чтения внутренних деталей формулируются:

- вход и предшествующее состояние;
- наблюдаемый результат;
- запрещённые исходы;
- ссылка на нормативного владельца;
- применимый архитектурный сценарий.

Для нового поведения создаётся protected test, который не проходит без реализации. Для исправления дефекта требуется доказательство:

```text
исходная версия + новый тест → FAIL
исправленная версия + тот же oracle → PASS
```

Ошибка импорта или отсутствие ещё не созданного API допустимы как начальный red-сигнал нового среза, но перед завершением тест обязан проверять наблюдаемое поведение, а не факт существования символа.

### 3. Реализовать минимальный путь

Код вводится небольшими порциями в рамках контракта среза. Implementer может добавлять unit, integration и property tests, но не ослабляет protected oracle для получения зелёного результата.

Fake-реализация является участником contract suite, а не эталоном поведения. Одни и те же контрактные проверки применяются к fake и реальному adapter настолько, насколько это допускает безопасная изоляция.

### 4. Сохранить локальные причины

Нетривиальная реализация получает Why-комментарий только когда разумное упрощение способно нарушить подтверждённое ограничение. Комментарий объясняет локальное следствие и ссылается на устойчивый нормативный раздел. Подробные правила находятся в [руководстве по Why-комментариям](why-comments.md).

### 5. Выполнить независимую проверку

Независимый verify является обязательным gate завершения каждого вертикального среза. Verifier начинает с чистого контекста и получает:

- контракт среза;
- применимые нормативные документы;
- итоговое изменение;
- protected tests;
- фактические результаты проверок.

Verifier не принимает историю рассуждений implementer как доказательство. Он ищет:

- oracle, выведенный из текущей реализации;
- ослабленные assertions, `skip`, `xfail` и слепое обновление snapshots;
- mocks, которые подменяют проверяемое поведение;
- одновременное согласованное ослабление fake и теста;
- расхождение кода, теста и Why-комментария;
- контрпримеры, переживающие существующий набор тестов.

Новая сессия того же агента допустима, если она не наследует implement-историю. Другой агент снижает коррелированную ошибку, но не становится источником истины. Verify-проход не исправляет production-код или oracle: при finding он возвращает срез implementer.

Verifier публикует:

```text
Slice:
Oracle sources:
Commands and results:
Counterexamples checked:
Documentation impact:
Findings:
Verdict: PASS | FAIL
```

`PASS` требует фактических доказательств обязательных результатов и отсутствия незакрытых findings. После любого исправления выполняется новый clean-context verify. Без `PASS` срез не завершается.

### 6. Проверить силу тестов

Для критических чистых функций и переходов состояния используются property-based и mutation-проверки. Цель — не общий процент, а обнаружение правдоподобных неправильных реализаций конкретного инварианта.

В первую очередь проверяются:

- продвижение cursor только после полного confirmed-набора сообщений плана;
- повтор с тем же `random_id`;
- cancel между внешними эффектами;
- bootstrap-граница;
- UTF-16 offsets и разбиение;
- учёт каждого `ContentItem` ровно одним допустимым результатом.

Конкретный mutation tool и каноническая команда выбираются только после появления кодовой базы и измерения времени полного suite.

### 7. Завершить срез

Перед завершением исполнитель:

1. запускает применимые проверки среза;
2. запускает полный доступный verify-профиль;
3. проверяет архитектурные границы;
4. сверяет жизненный цикл соседних Why-комментариев;
5. обновляет нормативных владельцев либо фиксирует `documentation impact: none`;
6. выполняет документационную проверку;
7. сообщает только фактически выполненные команды и результаты.

## Изменение protected oracle

Ожидаемое поведение protected acceptance или contract test меняется только когда:

- задача явно изменяет нормативное требование или публичный контракт;
- обнаружена доказанная ошибка самого oracle.

В обоих случаях сначала обновляется или подтверждается нормативный владелец. В отчёте фиксируются прежнее поведение, новое поведение и причина.

Без такого основания запрещены:

- ослабление assertion;
- добавление `skip` или `xfail`;
- расширение ожидаемого exception;
- принятие нового snapshot только потому, что изменился код;
- исключение неудобного edge case;
- вычисление ожидаемого значения тем же алгоритмом, что используется в production.

## Текущая стадия проекта

Кодовая база приложения и её канонические implementation-команды ещё не созданы. До их появления это руководство определяет порядок и доказательства, но не выдумывает структуру пакетов, имена test targets или команды CI.
