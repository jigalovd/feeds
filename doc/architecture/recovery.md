**Статус:** утверждено  
**Владелец фактов:** ошибки, повторы, отмена, конкурентность, точки входа и проверяемые сценарии  
**Читать когда:** меняется восстановление, конкурентность, отмена, наблюдаемость или архитектурная проверка  
**Связанные документы:** [карта архитектурной документации](README.md)

## Ошибки и повторы

Все внешние операции имеют ограниченный таймаут. Ошибки классифицируются:

- `retryable`;
- `permanent`;
- `server_required_wait`;
- `unknown`.

Для повторяемых ошибок используется ограниченная экспоненциальная задержка с jitter. Обязательная сервером задержка, включая Telegram FloodWait, соблюдается. Обычный пользователь эти параметры не настраивает.

Политика фаз:

- ошибка одного источника изолируется; остальные продолжаются, а delivery получает одно предупреждение;
- ошибка LLM завершает запуск до доставки; частичный синтез отбрасывается;
- доставка останавливается на первом конечном `failed` или неисчерпанном `unknown`.

Если построена `warning_summary`, любая уже отражённая в ней проблема не дублируется системным уведомлением независимо от наличия других units. Для остальных конечных проблем запуска создаётся не более одного безопасного агрегированного уведомления.

## Кооперативная отмена

`cancel(run_id)` сохраняет `cancel_requested`. Координатор проверяет его между внешними операциями:

- незавершённый capture прекращается без частичного `CaptureBatch`;
- complete batch сохраняется;
- незавершённый синтез отбрасывается;
- полный синтез может быть повторно использован только при точно том же наборе входных элементов и политике;
- во время доставки сохраняется результат текущего поздно завершившегося вызова, но новое сообщение не начинается;
- полностью подтверждённый план перед выходом продвигает связанные локальные cursors.

Внешние действия не откатываются, отправленные сообщения не удаляются.

## Конкурентные триггеры

Один системный mutex защищает полный запуск между процессами. Если ручной trigger приходит во время активного запуска, он возвращает типизированный результат `run_already_active` и не создаёт очередь или отложенный запуск.

Windows Task Scheduler настроен не запускать новый экземпляр поверх активного. Накопившееся содержимое остаётся после локальных cursors и обрабатывается следующим ручным или интервальным запуском.

Тот же `SystemLock` используется для миграции состояния, изменения несекретной конфигурации и изменения системного расписания. Дополнительные межпроцессные mutex не вводятся. Чтение статуса и диагностики не требует mutex. Запрос `cancel_requested` записывается атомарно через `StateStore` без захвата mutex, поэтому остаётся доступным во время полного запуска.

## Точки входа

- CLI предоставляет стабильные операционные команды запуска, отмены, повтора, статуса, панели и диагностики.
- Админ-панель вызывает те же прикладные операции через локальный API.
- Windows Task Scheduler вызывает `feeds run --scheduled`.

Точки входа не содержат собственных правил запуска, повторов или готовности.

## Наблюдаемость и безопасность

V1 использует структурированные безопасные логи с идентификаторами, кодами фаз и причин. Исходные тексты, секреты, токены и Telegram-сессия не журналируются. Точный срок и правила ротации безопасных метаданных определяет технический дизайн.

Распределённый tracing, event sourcing, lease-протокол и отдельный alerting framework не вводятся.

Локальная панель обязана сохранять loopback-only границу, защищаться от CSRF и DNS rebinding и не загружать внешние ресурсы. Секреты доступны только через `SecretStore`.

## Архитектура для ИИ-разработки

На старте достаточно корневого `AGENTS.md` с:

- четырьмя границами модулей;
- разрешёнными направлениями импортов;
- командами обязательной проверки;
- правилами секретов и долговечных фактов.

Локальный `AGENTS.md` появляется только когда модуль заметно вырос, получил отдельного владельца или требует специальных команд. Ограничение размера файла служит поводом для ревью, а не механической целью.

Автоматические архитектурные тесты должны запрещать обратные импорты и доступ к внутренностям соседнего модуля.

## Проверяемые сквозные сценарии

Минимальный набор:

| ID | Сценарий |
|---|---|
| `RUN-HAPPY-001` | полный успех одного элемента |
| `REC-RESTART-001` | восстановление после перезапуска |
| `CAP-SOURCE-FAIL-001` | ошибка одного источника |
| `SYN-FAIL-001` | ошибка синтеза |
| `DEL-MULTIPART-001` | multipart-unit |
| `DEL-UNKNOWN-001` | неизвестный исход отправки |
| `CURSOR-COMMIT-001` | cursor не продвигается до полной доставки плана и идемпотентно фиксируется после неё |
| `DEL-RECEIPT-CRASH-001` | авария после внешнего успеха до локального сохранения |
| `RUN-CANCEL-001` | отмена на capture, synthesis и delivery |
| `MON-BOOTSTRAP-001` | первый и повторный bootstrap |
| `RUN-CONFLICT-001` | конкурентный ручной trigger не создаёт второй или отложенный запуск |
| `OPS-DIAG-001` | временный безопасный DEBUG и diagnostic bundle без запрещённых данных |

Fake-реализации внешних портов обязаны позволять детерминированно ставить сбой до и после каждого внешнего эффекта.

ID сценария является устойчивой ссылкой для protected acceptance test. Один сценарий может иметь несколько test cases и property-проверок; число строк таблицы не задаёт число тестовых функций.

## Архитектурные инварианты

- Модулей ровно четыре: `monitoring`, `synthesis`, `delivery`, `operations`.
- Полным запуском владеет только `operations`.
- Предметные модули не вызывают друг друга.
- Telegram не проникает в контракт `synthesis`.
- Каждый complete `ContentItem` входит ровно в одну контентную unit.
- Локальные cursors продвигаются только после `confirmed` всех сообщений плана.
- Telegram unread-state и `readHistory` не используются.
- Незакрытый batch не теряется и не требует отдельного carry-over состояния.
- Частичный LLM-результат никогда не доставляется.
- План доставки после начала отправки неизменяем.
- В каждый момент исполняется не более одного полного запуска.
- Секреты существуют только в `SecretStore`.
