# Жизненный цикл полного запуска

**Статус:** утверждено  
**Владелец фактов:** сквозной поток, атомарность доставки, локальные cursors и bootstrap  
**Читать когда:** меняется последовательность capture, synthesis, delivery или продвижение cursor  
**Связанные документы:** [карта архитектурной документации](README.md)

## Сквозной поток запуска

```text
1. Захватить mutex либо завершить новый trigger как уже выполняющийся.
2. Восстановить незавершённые факты предыдущего запуска.
3. Выполнить одну серию recovery-повторов unresolved-сообщения.
4. Если старый план полностью подтверждён, продвинуть связанные локальные cursors.
5. Открыть и завершить `CaptureBatch` для каждого включённого источника.
6. Собрать элементы complete batches после текущих cursors.
7. Построить и провалидировать полный `SynthesisResult`.
8. Построить и целиком сохранить `DeliveryPlan` вместе со связью с входными batches.
9. Последовательно отправлять сообщения, сохраняя каждую квитанцию.
10. После `confirmed` всех сообщений плана атомарно продвинуть связанные cursors.
11. Сохранить `RunResult` и безопасное уведомление при конечной проблеме.
12. Освободить mutex.
```

Если units нет, план не отправляется и подтверждение элементов не выполняется.

## Атомарность доставки

`DeliveryUnit` группирует представление одного тега или сводки. Её сообщения отправляются последовательно, а один элемент никогда не делится между несколькими units. Границей продвижения локального прогресса является весь `DeliveryPlan`.

План неизменяем после первой отправки. Повтор использует тот же текст, сохранённые UTF-16 offsets и lengths entities, цель и `random_id`.

После первого сообщения с окончательным `failed` или неисчерпанным `unknown` новые сообщения плана не начинаются. Подтверждённые сообщения и полностью доставленные units сохраняются.

Unresolved считается первое по порядку сообщение начатого сохранённого плана с outcome `pending` или `unknown`, перед которым нет `failed`. `pending` включён намеренно: после аварии между внешним успехом и сохранением receipt локально остаётся именно это значение.

В начале следующего запуска `operations` выполняет одну настроенную серию повторов старого unresolved-сообщения с тем же `random_id`. Если исход всё ещё неизвестен:

- старый план закрывается с проблемой;
- его недоставленные элементы остаются `pending`;
- они входят в новый синтез;
- создаётся безопасная диагностика `possible_duplicate`.

Для v1 возможный повтор предпочтительнее молчаливой потери.

## Локальные cursors

`monitoring` хранит cursor каждого источника и предоставляет идемпотентную операцию:

```text
advance_cursors(batch_ids)
```

Каждый complete batch фиксирует `cursor_before` и `cursor_after`. `operations` вызывает продвижение только после `confirmed` всех сообщений связанного плана. Операция проверяет, что batch продолжает текущий cursor соответствующего источника, и атомарно записывает новые значения.

Повтор с уже применёнными batches идемпотентен. Telegram unread-state и `readHistory` не участвуют.

Если приложение завершилось после последнего delivery receipt, но до продвижения cursors, следующий запуск видит полностью подтверждённый план и выполняет только локальный commit без повторной отправки.

## Bootstrap

При первом включении источника `monitoring` задаёт временную нижнюю границу `captured_at - configured_interval`. Более старая история не создаёт `ContentItem` и не влияет на Telegram unread-state.

После полной доставки первого плана обычное продвижение cursor завершает bootstrap. Если capture не создал ни одного доставляемого элемента, cursor может быть продвинут после успешной фиксации пустого batch. Повторное включение источника начинает новый bootstrap.
