# Runtime и общая политика внешних операций

**Статус:** утверждено  
**Владелец фактов:** технический стек, поставка runtime и общая политика повторов  
**Читать когда:** меняются runtime, библиотеки, packaging или общая классификация внешних ошибок  
**Связанные документы:** [карта технической документации](README.md)

## Статус технического стека

V1 работает локально на Windows 11. Утверждены:

- CPython `3.14.x` x64 с обычной GIL-сборкой и диапазоном проекта `>=3.14,<3.15`;
- `uv` для разработки, разрешения зависимостей и lock-файла;
- один процесс с одним `asyncio` event loop и последовательным координатором `operations`;
- Telethon `1.44.x` как MTProto-клиент личного Telegram-аккаунта;
- асинхронный HTTPX как клиент облачного LLM;
- Pydantic v2 со строгой валидацией и `extra = forbid` для публичных и сохраняемых контрактов;
- Starlette `1.x` и минимальный Uvicorn `0.51.x` как embedded ASGI-стек локальной панели;
- SQLite через синхронные SQLAlchemy ORM 2.x и `pysqlite`;
- Alembic 1.x как единственный механизм изменения схемы;
- pywin32 312 как COM-доступ к Windows Task Scheduler;
- `regex` с фиксацией точной версии в lock-файле для границ extended grapheme clusters Unicode;
- PyInstaller `onedir` как самодостаточная поставка без установщика и автоматического обновления.

Точная patch-версия runtime и библиотек фиксируется lock-файлом сборки. Установленная поставка не скачивает зависимости во время запуска.

Внутренние неизменяемые значения могут быть dataclass-типами. DI-фреймворк не используется: реализации портов явно связываются в composition root.

Development/test group содержит pytest `9.x`, pytest-asyncio `1.x`, Hypothesis `6.x`, coverage.py с pytest-cov и Import Linter `2.x`. Эти зависимости не входят в поставку.

Поставка v1 распаковывается в отдельный каталог и не изменяется во время работы:

```text
<install-root>\
  Feeds-<version>\
    feeds.exe
    migrations\
    web\
    <runtime dependencies>
```

Один `feeds.exe` обслуживает CLI, админ-панель и запланированный запуск. Пользовательские данные хранятся отдельно:

```text
%LOCALAPPDATA%\Feeds\
  state.db
  secrets\
  logs\
```

Первый запуск создаёт локальную схему через Alembic. V1 не содержит встроенного протокола обновления, backup или rollback.

От выбора стека не зависят:

- одна локальная установка одного пользователя;
- отсутствие обязательного постоянно работающего сервиса;
- автоматический запуск без открытой админ-панели;
- Windows Task Scheduler как системный планировщик v1;
- небольшой операционный CLI без отдельного машинного schema-контракта;
- ввод секретов только через доверенный loopback-интерфейс;
- запрет бинарного анализа;
- продвижение локального cursor только после долговечно сохранённой полной доставки плана.

MCP-сервер не входит в runtime v1. Направление MCP выбрано для агентской интеграции после v1, но его runtime и протокол здесь не определяются.

## Повторы внешних операций

Общие классы:

- `retryable`;
- `permanent`;
- `server_required_wait`;
- `unknown`.

Повторы ограничены числом попыток и суммарным временем, используют экспоненциальную задержку с jitter. Требуемая сервером задержка соблюдается. Значения версионируются в технической конфигурации и не являются пользовательскими настройками.

LLM:

- context overflow уменьшает пакет;
- невалидный ответ получает один исправляющий повтор;
- окончательная ошибка пакета или merge завершает синтез;
- частичный результат отбрасывается.

Telegram:

- безопасные сетевые и RPC-ошибки повторяются;
- FloodWait до технического автоматического лимита ожидается;
- более долгий FloodWait завершает текущий шаг с `server_required_wait`;
- отозванная сессия создаёт `reauth_required`;
- ошибка одного capture-источника изолируется;
- Telegram unread-state не изменяется.

Фонового retry-worker нет. Повторы выполняет последовательный координатор при текущем запуске, начале следующего или явной команде `retry(problem_id)`.
