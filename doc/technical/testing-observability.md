**Читать когда:** меняются проверки, логирование, диагностика или правила удаления технических данных

## Тестовый стек

Единый test runner — pytest `9.x`. Асинхронные тесты используют pytest-asyncio `1.x` в `strict`-режиме; каждый тест получает отдельный function-scoped event loop. Конфигурация включает strict markers, strict config и import mode `importlib`. Параллельный запуск через xdist по умолчанию не используется.

Роли инструментов разделены:

- обычные unit-тесты проверяют чистую логику через собственные fake-порты и `unittest.mock`;
- Hypothesis `6.x` проверяет свойства Unicode-индексации и разбиения, state machine доставки, продвижения локального cursor, пакетирования и конфигурационных миграций;
- coverage.py с pytest-cov собирает statement и branch coverage, но не заменяет сценарные критерии;
- Import Linter `2.x` исполняет архитектурные контракты независимости предметных модулей, запрета обратных импортов и доступа к внутренностям соседнего модуля;
- отдельная mocking-библиотека не используется.

## Тестовые контуры и независимость oracle

Тестовые артефакты разделяются по полномочиям:

- protected acceptance tests проверяют наблюдаемое поведение из продуктовой приёмки и устойчивых архитектурных сценариев;
- port contract tests применяют один набор правил к fake и реальному adapter;
- developer tests поддерживают локальную реализацию: unit, integration и property tests;
- adversarial verification ищет контрпримеры через мутации, дополнительные свойства и независимый cold-read.

Ожидаемое поведение protected test прослеживается до нормативного владельца. Implementer не ослабляет его ради текущей реализации. Изменение семантики oracle требует изменения нормативного требования либо доказанной ошибки самого oracle.

Для исправления дефекта новый regression test обязан падать на исходной реализации и проходить с тем же oracle после исправления. Для нового поведения protected test создаётся до реализации и сначала подтверждает отсутствие требуемого результата.

Fake не определяет контракт. Общий contract suite проверяет fake и adapter на одинаковую семантику; безопасные live-проверки остаются отдельным ручным профилем.

Mutation testing применяется точечно к критическим чистым функциям и переходам состояния. Критерием является обнаружение правдоподобной ошибочной реализации инварианта, а не единый процент по всему проекту. Инструмент, пороги и команда выбираются после появления кода и измерения стоимости suite.

Независимый verify-проход является обязательным gate каждого завершённого вертикального PR-среза и дополняет, но не заменяет автоматические проверки. Входы, полномочия verifier, обязательный отчёт и семантика `PASS | FAIL` определены единственным владельцем процесса — [workflow разработки](../engineering/development-workflow.md#5-выполнить-независимую-проверку).

Milestone дополнительно проходит собственный gate на текущем интегрированном состоянии: все назначенные сквозные protected-сценарии, применимый полный verify-профиль и clean-context verdict. Один сквозной scenario ID может проверять результат нескольких PR-срезов; milestone gate не заменяет verify каждого из них.

Integration tests используют настоящие локальные реализации на изолированных ресурсах:

- repository и Unit of Work работают с отдельным временным SQLite-файлом;
- Alembic поднимает пустую БД до `head`, проверяет metadata и утверждённую дорелизную политику одной ревизии;
- HTTPX `MockTransport` моделирует LLM HTTP-протокол;
- HTTPX `ASGITransport` проверяет Starlette routes с явно запущенным lifespan;
- отдельные socket-тесты запускают настоящий Uvicorn на `127.0.0.1` и случайном порту для Host, Origin, cookie, CSRF, shutdown и runtime descriptor;
- Windows-only integration tests проверяют DPAPI, mutex и Task Scheduler adapter в изолированном namespace.

PyInstaller `onedir` проходит отдельный smoke-test на Windows из собранного каталога. Live Telegram и LLM проверки являются явными ручными smoke-тестами, требуют отдельного marker и никогда не входят в обычный CI-запуск.

## Диагностика и срок жизни

Логи имеют формат JSONL и строятся из типизированного allowlist. Разрешены время, безопасные технические ID, код события, фаза, outcome, код проблемы, счётчики и длительность.

Приложение использует стандартные уровни Python без собственных `TRACE`, `NOTICE` или `AUDIT`:

- `DEBUG` — дополнительные безопасные first-party события для диагностики;
- `INFO` — начало, завершение и штатный результат операции;
- `WARNING` — неожиданное или деградированное состояние, при котором соответствующая функция продолжает работать;
- `ERROR` — конкретная функция или операция не выполнена, но процесс ещё способен безопасно обработать результат;
- `CRITICAL` — процесс не может безопасно продолжить работу и завершается.

Порог по умолчанию — `INFO`. Уровень и допустимые поля задаются единым каталогом `event_code → level + allowed_fields`, а не выбираются произвольно в месте вызова. `attention_required` остаётся независимым прикладным признаком и не выводится из log level.

Production-поставка содержит расширенные `DEBUG`-события, но они выключены по умолчанию. `diagnostics debug enable` атомарно сохраняет `debug_until_utc = now + 60 minutes` в техническом состоянии. По истечении срока порог автоматически возвращается к `INFO`; повторный enable начинает новый срок. Status и disable не требуют раскрытия конфигурации или секретов.

DEBUG применяется только к first-party логгерам `feeds.*`. Он не меняет настройки Telethon, HTTPX, SQLAlchemy или Uvicorn, не включает access log или SQL echo и не допускает необработанные сообщения внешних библиотек. Расширенный режим добавляет только больше типизированных событий, переходов и timings в рамках того же allowlist. Эти записи могут входить в diagnostic bundle на общих основаниях.

Запрещены:

- исходное содержимое публикаций;
- промпты, модельный результат и финальный текст доставки;
- entities, usernames, phone, URL и Telegram raw IDs;
- `access_hash`, ключи, Telegram-сессия и значения секретов;
- HTTP headers, request/response bodies и значения конфигурации;
- необработанный текст исключения внешней библиотеки.

Исключение журналируется как тип, безопасный внутренний код и first-party stack frames без locals, строк исходного кода и исходного message.

Пока delivery или продвижение cursor могут восстанавливаться, сохраняются минимально необходимые тексты, batches, план и квитанции. После закрытия обязательств немедленно удаляются:

- исходные тексты;
- сформированные сообщения и entities;
- модельные запросы и ответы, если они сохранялись;
- данные, нужные только для повтора.

Логи ротируются по дню и размеру; файлы старше 30 дней удаляются. Незавершённое обязательство не удаляется по календарному сроку без явного административного решения.

Diagnostic bundle содержит только разрешённые логи, безопасный статус, версии компонентов и результаты проверок. Он не содержит БД, конфигурацию, секреты или содержимое.

CLI, планировщик и панель получают одинаковый `RunResult` и безопасный `RunProblem`. `attention_required` является флагом проблемы.
