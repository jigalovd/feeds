## Долговечное состояние

`StateStore` хранится в `%LOCALAPPDATA%\Feeds\state.db` и является единственным хранилищем долговечного несекретного состояния, включая секционированную конфигурацию. Состав фактов и их переходы определяет архитектурный дизайн; ORM-модель не становится дополнительным публичным контрактом.

Доступ к состоянию реализован через синхронные SQLAlchemy ORM 2.x, `pysqlite` и явные repository-классы:

- ORM-модели приватны для владеющего данными модуля;
- публичные API не принимают и не возвращают `Session` или ORM-объекты;
- межмодульные идентификаторы и внешние ключи допустимы;
- межмодульные ORM relationships запрещены;
- агрегатор Alembic metadata является единственным разрешённым техническим импортом всех ORM-моделей.

Используется `sessionmaker(expire_on_commit = false, autoflush = false)`. Unit of Work явно выполняет commit или rollback. Транзакция локальной БД никогда не удерживается во время сетевого вызова: намерение и наблюдаемый результат сохраняются отдельными короткими транзакциями.

Для каждого соединения устанавливаются:

```text
foreign_keys = ON
journal_mode = WAL
synchronous = FULL
busy_timeout = 5000
```

Долговечные незавершённые обязательства не удаляются по календарному сроку. Безопасные метаданные закрытых запусков очищаются через 30 дней.

## Миграции схемы

Alembic является единственным владельцем схемы. Runtime не вызывает `create_all`; новая пустая БД создаётся только через `alembic upgrade head`. Autogenerate разрешён как черновик, но результат всегда проверяется вручную. SQLite-изменения используют `render_as_batch`, когда прямой `ALTER TABLE` недостаточен.

До релиза v1 существует ровно одна редактируемая ревизия:

```text
migrations/versions/0001_v1_baseline.py
down_revision = None
```

Создание второй ревизии до v1 запрещает CI. Изменение дорелизной схемы редактирует baseline, а локальная дорелизная БД сбрасывается и создаётся заново; совместимость с ней не поддерживается. При выпуске v1 baseline замораживается. После v1 каждое изменение получает новую последовательную миграцию.

Первый запуск новой установки выполняет `alembic upgrade head`, затем SQLite `quick_check` и `foreign_key_check`. Production upgrade, backup, restore и rollback проектируются отдельно перед первым обновлением установленной версии.

CI проверяет отсутствие незапланированной новой ревизии до v1, актуальность metadata через `alembic check` и миграцию пустой БД до `head`.

## Конфигурация

Несекретная конфигурация хранится в `state.db` как один версионированный агрегат:

```text
schema_version
revision
monitoring
synthesis
delivery
scheduling
admin
secret_refs
```

Каждая секция имеет строгую Pydantic-схему; неизвестные поля запрещены. Конфигурация содержит только ссылки на секреты. Внутренние retry-политики являются кодовой политикой и пользовательскими настройками не становятся.

Запись выполняется одной SQLite-транзакцией под общим `SystemLock`. Изменяющая операция принимает `expected_revision`; устаревшая ревизия возвращает конфликт и не повторяется автоматически.

Отсутствующая или невалидная конфигурация не заменяется значениями по умолчанию молча. Система показывает типизированную проблему. Изменение структуры агрегата выполняется Alembic-миграцией вместе с остальной схемой; отдельного механизма миграции конфигурационного файла нет.
