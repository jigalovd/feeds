# Приёмка первой версии

**Статус:** утверждено  
**Владелец фактов:** бизнес-критерии, порядок реализации и стратегия приёмки v1  
**Читать когда:** меняются выпускные критерии, проверяемые продуктовые инварианты или порядок вертикальных срезов  
**Связанные документы:** [карта продуктовой документации](README.md)

## Критерии достижения бизнес-цели

Первая версия достигает цели, если:

- пользователь один раз авторизует личный Telegram-аккаунт;
- каналы, промпт, получатель, модель и расписание меняются без изменения кода;
- ручной и запланированный запуск применяют одинаковые правила;
- каждый подходящий элемент отражён в дайджесте либо явно учтён как реклама или детерминированный элемент;
- межпоточные дубли объединяются без потери ссылок;
- противоречия не скрываются;
- Telegram unread-state не изменяется, а локальный cursor продвигается только после полной подтверждённой доставки плана;
- секреты отсутствуют в конфигурации, выводе CLI, уведомлениях и логах;
- автоматический запуск работает без открытой админ-панели;
- `synthesis` можно использовать с другим платформенным адаптером без изменения его контракта;
- получение и доставка можно изменять независимо друг от друга.

## Порядок реализации первой версии

Проект реализуется вертикальными проверяемыми срезами:

1. один `ContentItem` проходит `capture → synthesis → delivery → cursor advance` на fake-адаптерах;
2. тот же сценарий восстанавливается после перезапуска из долговечного реестра;
3. подключается реальный Telegram happy path для одного источника и одной delivery-unit;
4. добавляются реклама, теги, дедупликация, конфликты, `model_view` и пакетирование;
5. закрываются частичная доставка, unknown outcome, отмена, bootstrap и ошибки источников;
6. добавляются SecretStore, админ-панель, CLI и вычисляемая readiness;
7. подключается Windows Task Scheduler;
8. закрывается пользовательский контур безопасной диагностики: временный DEBUG и diagnostic bundle.

Каждый срез заканчивается исполняемым сквозным сценарием. Универсальная интеграционная платформа и адаптеры будущих платформ заранее не проектируются.

Безопасное структурированное журналирование развивается вместе со всеми срезами. Срез 8 добавляет пользовательские операции диагностики и доказывает, что расширенный режим и diagnostic bundle не раскрывают запрещённые данные.

## Стратегия приёмки первой версии

V1 оценивается по детерминированным и автоматически проверяемым инвариантам. Ручная оценка качества резюме, стабильность названий тегов и субъективная полезность `model_view` не являются выпускными критериями.

Исполняемый тест подтверждает критерий приёмки только тогда, когда его ожидаемое поведение прослеживается до этого документа или другого применимого нормативного владельца и не было выведено из проверяемой реализации. Тесты являются доказательствами выполнения требований, а не самостоятельным источником продуктового поведения.

Каждый проверяемый запуск обязан подтверждать:

- валидность всех версионированных контрактов и схем;
- учёт каждого входного `ContentItem.item_id` ровно одним допустимым результатом;
- отсутствие скачивания, хранения и передачи бинарных данных модели;
- сохранность всех обязательных `OriginReference`;
- ровно один основной тег для каждого содержательного элемента;
- обязательный `model_view` либо стандартную фразу об отсутствии вывода;
- наличие `ad_evidence` для каждой исключённой рекламной публикации;
- смысловое объединение только между разными потоками;
- сохранение обозначенных моделью конфликтов;
- корректное представление Telegram `text + entities` и соблюдение предела каждой части;
- отсутствие потери элементов при пакетировании, объединении и разбиении;
- отсутствие доставки частичного LLM-результата;
- отсутствие продвижения cursor до `confirmed` всех сообщений плана;
- отсутствие вызовов Telegram `readHistory` и изменений внешнего unread-state;
- сохранение позднего результата уже начатого внешнего вызова после ручной отмены;
- предсказуемое восстановление после каждой поддерживаемой ошибки;
- отсутствие секретов и исходных текстов в небезопасных интерфейсах и журналах.

Детерминированная приёмка проверяет выполнение структурированного контракта, но не доказывает смысловую правильность классификации, объединения, тегов, резюме или выводов. Это осознанное ограничение v1.

Максимальное время запуска, токены и денежная стоимость могут измеряться и ограничиваться технической конфигурацией, но не являются бизнес-критериями выпуска.
